## Problem Statement
QuietOps is live and looks like a real on-call console, but experiment #610 has **1 exposure** (as of
2026-11-26 10:51 UTC). Track 01 is judged mainly on the experiment: clear hypothesis, real events,
explainable results. A rival entry, Rollback Drill (on-call game + A/B test, 75 s, "pick which deploy to
roll back"), is recruiting from the same hackathon Discords with a sharp post. Our real players come only
from those Discords. Players, not features, decide this.

One visual bug also hurts variant B: in the blast-radius map, straight edges cut through node labels
(`web-frontend → cdn` passes through `api-gateway`), five arrowheads pile into a blob on top of
`db-primary`, and `inventory-svc` / `db-replica` almost touch.

## Premises (agreed)
1. Players are the bottleneck. Every remaining hour either gets more first-round players or makes the result
   easier to explain.
2. A big effect needs fewer players. The scenario and both variants are frozen once v3 starts.
3. The winner rule is written down **before** results come in (below), and shown on /results.
4. Simulated traffic goes to the **Development** environment only, labelled as simulated. It never feeds the verdict.
5. Recruiting happens on the result screen, after the counted round, without revealing the other variant.
6. Recruiting is Michael's #1 task.

## Approaches Considered
- **A: Rigor only.** Decision rule + simulator, no player-facing change. Rejected: no help getting players.
- **B: "Here's what the other half saw" reveal.** Rejected by the user: players would learn about the
  split and tell friends before they play ("flagsmith is supposed to be used ... anonymously").
- **C: Paste-your-own-alerts grouping page.** Rejected: big Impact story but takes time from the experiment.

## Chosen: B-lite + map fix

### 1. Map fix + clickable map (grouped only) — FIRST, then restart
File: `src/components/dashboard/DependencyMap.jsx` (+ `GroupedView.jsx`, `styles.css`).
- **Hand-placed layout** for this scenario: a `LAYOUT` map of service id → (col, row) inside DependencyMap,
  falling back to the current auto-layout for any service not listed. Layout is presentation only;
  `incident.json` is unchanged. Rules: dependencies still flow top → bottom; `db-primary` shares the bottom
  row with `redis-sessions` and is not enlarged, coloured or labelled differently from other involved
  services. (`cdn` moved up beside `api-gateway`: its only caller is `web-frontend`, and keeping it in the
  bottom row forced a long edge through the middle of the map.)
- **Curved edges** (cubic Bézier `path`s instead of `line`s) routed so no edge crosses a node box.
- **Spread arrowheads:** each edge lands at its own point along the target box's top edge (spaced by the
  order of the source's x), so 5 edges into one box stay distinct.
- **Spacing:** no two boxes closer than ~16 px; map uses more of the panel height on desktop.
- **Clickable nodes (involved services only):** click/tap, or Enter/Space when focused, selects the service:
  - its row in the incident list expands and scrolls into view (`scrollIntoView({block:'nearest'})`),
  - every edge touching it (calls in and out) gets the highlight style, others dim,
  - clicking a row still selects its node (existing behaviour). Clicking the selected node again clears it.
  - Nodes are `role="button"`, `tabIndex=0`, with `aria-label="{service}, {n} alerts"`.
  - Idle (uninvolved) nodes are not clickable.
- **Fairness checks (unchanged rules):** no text, colour, size, order or animation singles out a likely cause.
  Highlight colours apply equally to whatever the player selects.

### 3. Pre-registered winner rule (shown on /results and in the demo)
Decided at **Sat Nov 28, 2 PM PT** on experiment v3, primary metric 585 *Found root cause*:
- **Grouped wins** if Flagsmith's probability that grouped beats control is **≥ 80%** *and* grouped's wrong-diagnosis
  rate (586) is not more than 10 points worse → roll out grouped **10% → 50% → 100%**.
- **List wins** if that probability is **≤ 20%** → keep control at 100%.
- **Otherwise: inconclusive.** Keep control, say so plainly, and report the observed rates and player counts.
- Fewer than 30 players per variant at decision time → inconclusive regardless.
- Why 80%, not 95%: the change is a reversible UI layout behind a flag with a kill switch, so the cost of a
  wrong call is low. This is stated on /results so judges see the reasoning, not just the number.

### 4. /results upgrades (lead)
`src/components/results/ResultsPage.jsx`:
- The winner rule above, verbatim.
- "Players so far: N / 60" progress bar (N = exposures across both variants; 60 = 30 per arm).
- Split health: "50/50 split looks healthy" when `srmPValue` ≥ 0.01, a warning otherwise, hidden when null.
- One plain-English line on where the data stands now (e.g. "Grouped 64% vs list 41% found the root cause;
  73% probability grouped is better. Not decided yet.").
- Rollout tracker: after the experiment ends, shows the grouped share served (10 / 50 / 100%). Source: the
  feature state's multivariate weights through the existing admin-key API (`api/results.js`), added to the
  response as `rollout`. Shown only after the experiment status is completed.
