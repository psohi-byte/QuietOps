## Problem Statement
QuietOps works end to end (Flagsmith experiment 595 running, events verified), but the whole game looks
like a quick template: system fonts, flat identical grey boxes, no motion, no product identity, a plain
centered intro. The grouped variant is also hard to read: the map lights 8 of 10 services in alarm red,
"Cluster 1" still dumps 20 of 26 alerts in one list, cluster names mean nothing, and nothing says where to
look first. For the demo video and the Impact score, the game has to look like a tool an on-call engineer
would recognise.

## What Makes This Cool
You get paged at 2:16 AM, acknowledge, and land in a console that looks like the real thing, with alerts
streaming in. Half the players get a raw alert feed. The other half get the same alerts consolidated into
one incident with a blast-radius map. Flagsmith tells us, with real players, which layout finds the root cause.

## Premises (agreed)
1. The grouped view fails on presentation, not the idea. A fair test needs the best honest version of grouping.
2. "Better" never means "gives the answer." No root-cause or "probable origin" label, and **no ordering or
   labelling that lets a player answer without reading the alerts** (e.g. no "+0s" anchor, no sort by first-seen).
3. Because B changes, experiment 595 ends and a fresh experiment (v2) starts on the new build.
4. The visual redesign applies to **both** variants equally. The only difference between A and B stays the
   alert body component (`ListView` vs `GroupedView`).
5. ~~Demo link to force a variant~~. **Rejected by the user:** random assignment is the point. Demo
   recording uses the existing dev-only `?variant=` override on localhost.

## Approaches Considered
- **A: Polish pass.** Same layouts, better type, icons and motion. Fastest, but still reads as a template.
- **C: Cinematic game.** CRT style, sound, shake. Distractions undercut the alert-fatigue story and the
  "real tool" credibility.

## Recommended Approach: B, a believable on-call console (chosen)

### Shared shell (identical in both variants)
- **Type and tokens.** Inter (UI) + JetBrains Mono (data) via Google Fonts. Surfaces: base `#0B0E14`,
  `--panel` `#11151E`, `--surface-2` `#171C27`, `--border` `#232A38`. Reuse the existing `--mono`, `--border`
  and `--info` (no duplicates). Add only `--surface-2` and `--font-ui`.
- **Intro (2 AM page).** A phone-lockscreen-style pager card showing:
  - the time "2:16 AM"
  - "QuietOps · SEV-1 · {title} · {alerts.length} alerts firing" (counts from `incident.json`). `{title}` is
    `scenario` with its "SEV-1: " prefix stripped, as `App.jsx` already does.
  - an "Acknowledge" button and the 3-step how-to underneath

  Intro text still comes from `game_config.introText`. An optional single CSS shake goes first in the cut order.
- **Incident header.** Sticky: SEV-1 badge, title, "Investigating" status pill, monospace countdown (red at
  <=10s), primary "Diagnose" button. **No sidebar or icon rail** (cut: inert nav invites wasted clicks and
  differs between desktop and mobile).
- **AlertRow.** An inline-SVG severity icon (critical / warning / info) replaces the text pill. Service in
  `--mono`, then message, then absolute time. One component, used by both variants.
- **Entrance animation.** Fixed total of **1.2s in both variants**. The animated items are each alert row (A),
  and each service row plus each map node (B). Per-item delay = `1.2s / itemCount`, computed per container.
  Panel headers don't animate. Under `prefers-reduced-motion`, no animation.
  The timer starts when the console mounts, in both variants, exactly as now.
- **Diagnose overlay.** A command-palette-style "Declare root cause" with the 4 choices in
  `incident.choices` order (same in both).
  - Keys 1-4 select a choice and Esc closes; they are active **only while the overlay is open**.
  - On open, focus moves to the **dialog container**, not a choice, so a stray Enter or Space can't answer.
    Focus returns to the Diagnose button on close.
  - Selection goes through the existing `finish()` and its `finished` guard, so no double fire.
- **Result screen.** Michael's component, unchanged. It inherits the fonts and tokens through the variable names.

### Variant A (control): list, newest first
Layout and ordering unchanged: one feed, newest first, in the new row style. Panel header: "{n} alerts firing ·
newest first". No new features, so A gets only the visual upgrade.

### Variant B (grouped): incident card + blast-radius map
- **Incident card.** Header "Incident · {count} related alerts · {services} services". It's derived from the
  largest alert group, which is `g1` in this scenario; the code picks it by size rather than hardcoding the id.
  - **One row per service, ordered by alert count (descending), ties by name.** Not by first-seen time,
    because the earliest service in the incident is the answer.
  - Each row shows: service (mono), alert-count chip and worst-severity icon. **No time on collapsed rows**:
    with only 8 rows, a per-row first-seen time would make the earliest service (the answer) readable at a
    glance. Times appear only on individual alerts once a row is expanded, the same as A shows them.
  - Tap or click a row to expand that service's alerts (oldest first). All rows start collapsed. Tapping a row also
    highlights that node on the map. One direction only: map nodes aren't interactive.
- **Blast-radius map.** The existing SVG `DependencyMap`, restyled.
  - Services in the incident use **one neutral "involved" style**: an amber outline and a severity-coloured
    count badge. They aren't filled alarm red.
  - Uninvolved services are dimmed, and edges between involved services are highlighted.
  - No time offsets or labels on nodes. Legend: "→ calls".
  - The selected row's node gets an accent outline.
- **Other groups.** A collapsed section "2 other alert groups · {n} alerts", each named in code from its services
  ("cdn", "auth-svc + redis-sessions"). The word "unrelated" is deliberately not used, because it would hint that
  `cdn` (one of the 4 choices) is wrong. `cdn` also appears in the incident (its origin-504 alert). That's
  realistic and acceptable.
- **Data.** `incident.json` group labels are not shown; names and counts are derived in code. No data changes.
- **Banned:** any text naming, ranking or time-anchoring a likely cause.
- **Layout:** side by side at >=960px. Below that the map sits on top, scaled via `viewBox`.

### Exposure fix (required for v2)
Today `start()` calls `getDashboardVariant()` (which calls `getExperimentFlag` and records an exposure) on **every**
round, before `startRound()`. Returning players would log v2 exposures that can never convert, diluting both arms.
Change:
- call `startRound()` first
- if `counted`, call `getExperimentFlag` (exposure)
- otherwise read the value with `flagsmith.getValue` (no exposure)

**Verified in SDK source:** in `@flagsmith/flagsmith` 12.6.0, `src/flagsmith-core.ts`:
- `getExperimentFlag` calls `trackExposureEvent` (line ~1064), and only when the flag is enabled, loaded from the
  server and `experiment.inExperiment` is true.
- `getValue` (line 700) never records an exposure.

v1 players already have `quietops_rounds_started >= 1`, so they will never record v2 exposures. They've
seen the answer, which is correct.

   3. Create v2 on `dashboard_variant`: same hypothesis, 50/50, the same metrics. Those are 585 Found root cause
      (`incident_resolved_correctly`), 588 Time to correct diagnosis (mean of that event's `value` = seconds),
      586 Wrong diagnosis (`incident_resolved_incorrectly`) and 587 Timed out (`incident_timed_out`).
   4. Start v2.

   Right after ending 595, confirm with `flagsmith evaluate` (or the identities API) what `dashboard_variant`
   serves during the gap. Expected: the default, `control`, with `in_experiment` false. Nobody is exposed during
   the gap, since `getExperimentFlag` skips non-enrolled players.
   **Accepted loss:** a first-time player in the ~5 min gap uses up their one counted round and never enters v2.
4. On the live site, verify one round with `?debug=1`: exposure, then event (202).
5. Record the v2 id in Claude memory and in the header comment of `src/lib/flagsmith.js`. Send it to Michael
   for his README (he owns that file).
